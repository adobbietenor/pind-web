For an **independent adversarial review**: a fresh Claude Code session with no prior
context, tasked only with finding leaks (decisions.md Part 5, Alex). Alex has agreed
the rules in plain English (`docs/visibility.md`). Your job is to find any way a
visitor, a signed-in person or someone holding their own session token can read,
infer or change what those rules say they must not — and whether the tests would
catch it. Report each leak with the rule it breaks and a concrete reproduction (a
failing harness case is best). Do not fix anything yourself; fixes come afterwards
as new migrations. Work against pind-staging only, never production. This review,
plus Alex's own read of `docs/visibility.md`, must be done before T6 (the pinned

## What to check

**The core rule**
- `private.can_see_at` is the only place that decides person-to-person visibility.
  Check all five conditions of V1: published, both opted in, no block either
  direction, neither hidden, list still open (effective end + 24h).
- Every policy that exposes another person's data goes through it:
  `people_read_visible`, `pins_read_visible`, `pin_friends_read_claimed_visible`,
  `photos_read_visible` (via `private.can_see_photo`), and the report insert check.

**Security-definer functions**
- Every function in `private` has `search_path = ''`, and all but the photo-reset
  trigger are `security definer`. Check each one answers only about the current
  session's person (`private.me()`) or returns a boolean, so none of them can be used
  to enumerate people.
- `private` is not in PostgREST's exposed schemas, so visitors cannot call these
  directly. Only the functions granted to `authenticated` at the end of the functions
  migration are usable, and only inside policies.
- The public functions `gathering_counts`, `women_only_offer` and `spot_poll` must
  return aggregates or a boolean only. `gathering_counts` is callable by `anon`.

**Privileges (the column layer)**
- The policies migration starts with `revoke all on all tables in schema public from
  anon, authenticated`. Check the grants that follow: no `select` on `reports`,
  `magic_links`, `outbound_messages`, or any app-phase table; `pin_friends` select
  excludes `claim_token_hash` and `age_attested_at`; visitors cannot write
  `people.hidden_at`, `people.photo_status` or `reports.status`.
- Grants are layered under RLS: a policy can only narrow what the grant allows.

**Things we decided that look odd in SQL**
- The gender mix's `other` is `open − women − men`, null when zero or when fewer than
  5 are open (V3). It is not a count of `nonbinary` + `undisclosed`, so a person with
  no `people_private` row still lands in a bucket and the three always sum.
- `women_only_offer` returns a boolean on purpose; there is no women-only count
  anywhere (V5).
- `hidden` people count in `pinned` but not in `open_to_meeting` (V2).
- Report auto-hide counts **distinct reporters**, and ignores dismissed and actioned
  reports.

**Known limits (accepted, documented in visibility.md)**
- Someone allowed to see a photo can mint a long-lived signed URL with their own
  session token. The 5-minute lifetime is a Worker convention.
- Live counts and a small "Other" can hint at one person. Mitigated by never
  ordering the T6 list by join time.
- Supabase's default privileges still grant future tables to `anon`/`authenticated`.
  New tables stay locked only because RLS is enabled with no policies. The app
  phases should keep adding explicit grants.

## How to run the harness

Requires Node from `.nvmrc` and `npm install`. `.dev.vars` needs `SUPABASE_URL`
(bare pind-staging URL), `SUPABASE_SERVICE_ROLE_KEY` (secret key) and
`SUPABASE_PUBLISHABLE_KEY`. Anonymous sign-ins must be on for the project.

```
npm run test:policies
```

- It refuses to run unless `SUPABASE_URL` is pind-staging (`mxuajvlrkggrqpntekqt`).
- It builds a cast of 37 people across 7 gatherings with the service key, signs
  18 of them in (2 anonymously), and runs every case with each person's own session
  through the REST and Storage APIs.
- Everything it creates is tagged (`pindhx` prefix) and swept away afterwards, including
  after a crashed run: the next run sweeps first.
- One run takes about 30 seconds. Supabase rate-limits sign-ins per IP (anonymous:
  30 per hour), so avoid running it many times in a row.
- It creates rows in staging, so two people should not run it at the same moment.

`npm run typecheck` type-checks the Worker and the harness.

## How we know the harness catches leaks

Before the migrations were applied, the harness failed at setup, as it should. After
they were applied, all 38 cases passed. As a check on the tests themselves, a
throwaway copy that swapped the "wrong person" in five CANNOT cases (P09, P11, P15,
P25, P36) for the service key failed exactly those five cases. So the assertions do
detect a leak.

## Applying the migrations

Already applied to pind-staging with `npx supabase db push`. Production has not been
touched.

## M1.2 addendum — admin (for the same review)

Same process: rules in `docs/visibility.md` (§12 V11 publishing rules, §12b V12
admin-only data, §16 table), SQL in the four `20260918154…_m1_2_*` migrations,
harness cases P38–P47.

**SQL to check**
- `m1_2_admin_privileges`: every new table is `revoke all` from `anon` and
  `authenticated` (Supabase grants new tables to them by default); only `cities` is
  granted back (read). The `venue-maps` bucket is public-read with **no** storage
  policies for visitors, so they cannot write, replace, delete or list.
- `m1_2_admin_functions`: `private.gathering_status_rules` (trigger) — publish needs a
  venue with 3 active spots, unpublish needs zero pins, a published venue cannot
  change, a merged gathering cannot be restored. The `admin_*` functions are
  security **invoker**, executable by `service_role` only (explicitly revoked from
  `public`, `anon`, `authenticated`); check none can be called by a visitor (P41) and
  that `admin_set_photo_status` only acts on the exact `photo_path` shown (P46).
- `gatherings.status` is derived; `published_at` is still the only thing policies and
  `gathering_counts` look at, so no M1.1 policy changed.

**Worker to check** (not SQL, but it is the admin's lock)
- `src/admin/access.ts`: RS256 signature against the team's keys, issuer, audience,
  expiry, email allowlist; refuses when unconfigured. Unit tests
  `tests/unit/access.test.ts` (A01–A12).
- `src/admin/origin.ts`: writes accepted only on `Sec-Fetch-Site: same-origin`, or
  without it only on an exact `Origin` match. Unit tests `tests/unit/origin.test.ts`
  (O01–O06). A first version refused every admin form (`Referrer-Policy: no-referrer`
  made browsers send `Origin: null`); fixed in `6c9407c`.
- The admin reads people with the service key: it is the one surface that sees
  everything, which is why both locks exist.

Run: `npm run test:policies` (48 cases) and `npm run test:unit` (24 cases).

## M1.3 addendum — Ticketmaster import and the withdrawn state (for the same review)

Rules in `docs/visibility.md` (§12c V13 withdrawn, §12d importer rights, §15 table,
§16 map), SQL in the three `20260918192…_m1_3_*` migrations, harness cases P48–P54.

**SQL to check**
- `m1_3_import_schema`: `import_runs`, `gathering_flags` and `gathering_withdrawals`
  are `revoke all` from `anon` and `authenticated`, with no policies (P48). The
  withdrawal *reason* ("takedown") is in `gathering_withdrawals`, never on the public
  `gatherings` row; the public row only gains `withdrawn_at`. `venues.latitude/longitude`
  are public (venue coordinates, H4 allows them). `gatherings.status` was re-created to
  add `withdrawn`.
- `m1_3_withdrawn_visibility` — **this changes M1.1 functions and policies**:
  `private.is_published` and `private.list_open` now also require `withdrawn_at is
  null`; `gatherings_read_published` lets a withdrawn row through only to someone
  pinned there (`private.i_am_pinned_at`, security definer, granted to anon and
  authenticated); `gathering_spots_read_published` hides a withdrawn gathering's spot
  options from everyone; `public.gathering_counts` returns a withdrawn gathering's
  counts only to someone pinned there. Look for any path that still treats a withdrawn
  gathering as live (P49–P51), and whether `i_am_pinned_at` leaks anything by itself.
- `m1_3_import_functions`: every function is security **invoker** and executable by
  `service_role` only. `admin_import_apply` re-checks state on every write: drafts
  only for date moves and dismissals, restore only when the last dismiss/restore log
  entry is the importer's, flags only on published, non-withdrawn gatherings (P52).
  `admin_purge_ticketmaster_data` deletes only never-published, Ticketmaster-only
  gatherings with no pins (P53). `admin_merge_venues` refuses a venue with a published
  gathering or meeting spots (P54).

**Worker to check**
- `src/import/` runs with the service key (cron and the admin button), never on behalf
  of a visitor. Ticketmaster and Anthropic keys are Worker secrets; the Ticketmaster
  key travels in the query string (the API requires it) and never appears in an
  error message (`tmclient.ts`).
- Event and venue names from Ticketmaster go to Claude as JSON data; the answers are
  parsed strictly (`ai.ts`, unit tests A01–A06) and only ever land in admin-only tables.
- New admin routes (`src/admin/routes.ts`, M1.3 block) sit behind the same Access and
  same-origin checks in `guard.ts`, which run before routing.

Run: `npm run test:policies` (55 cases) and `npm run test:unit` (55 cases).
